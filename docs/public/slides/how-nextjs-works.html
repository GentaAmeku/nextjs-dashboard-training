新人エンジニア向け / 仕組み編

Next.js のウェブアプリは
どうやって動くのか？

「画面が出る」その裏で、ブラウザとサーバーが何をやり取りしているのか。
手を動かす前に、仕組みを絵でつかみましょう。

🎯 このスライドで分かること
  • ブラウザとサーバーが何を往復しているか
  • Server Component と Client Component の違い
  • 1回のアクセスで何が順番に起きるか（リクエストの旅）
  • ルーティング・データの流れ・キャッシュ・認証の概要
STEP 1 / 大前提

ウェブアプリ＝「ブラウザ」と「サーバー」の往復

あなたが見ている画面は、遠くのサーバーに「ください」とお願いし、返ってきたものをブラウザが組み立てたもの。レストランの注文に似ています。

ブラウザ 客席
あなたの手元。画面を表示し、クリックなどを受け付ける。
⇄リクエスト / レスポンス
サーバー 厨房
注文を受けて調理（処理）し、できあがり（HTML/データ）を返す。

この「どこで調理するか（サーバー？ブラウザ？）」の配分が、Next.js を理解するカギです。

STEP 2 / 比較

従来の React は「全部ブラウザで」やっていた

CSR 従来のやり方
① ほぼ空の HTML が届く
② 大きな JavaScript を全部ダウンロード
③ JS が DB に問い合わせ → ようやく描画
⚠️ 困りごと
  • 最初の表示が遅い（JS を読み終えるまで真っ白）
  • JS が重くなる（DBアクセス等もブラウザへ）
  • 秘密が漏れる恐れ（鍵やトークンがブラウザに）

→ 「なんでもブラウザ」をやめて、サーバーでできることはサーバーでやろう、というのが次の発想。

STEP 3 / 発想の転換

Next.js は処理を「サーバー」と「ブラウザ」に分担する

最初の重い仕事（データ取得・HTML 組み立て）はサーバーで済ませてから送る。ブラウザは仕上げと操作に集中する。

サーバー で完成に近づける
DBから取得し、HTMLをほぼ組み立てて送る。送るJSが減る。
→完成済みHTML＋必要なJSだけ
ブラウザ で仕上げる
すぐ表示。あとからボタン等の操作部分だけJSを有効化。

この仕組みの中心が React Server Components（RSC） です。

STEP 4 / 主役

2種類のコンポーネント：どっちで何をする？

Server Component 既定
  • サーバーで実行（書くだけ・指定不要）
  • DB に直接アクセスできる
  • async/await でデータ取得
  • ブラウザに送る JS を減らせる
Client Component "use client"
  • ブラウザで実行
  • useState / onClick が使える
  • クリックなどの操作を担当
  • DBの鍵などは持たせない

迷ったら：表示・取得＝Server / 操作・状態＝Client。Serverの中に必要な部分だけClientを置く。

STEP 5 / いちばん大事

1回のアクセスで起きること（リクエストの旅）

ブラウザが /tasks にアクセス — URLを入力 / リンクをクリック
Edge proxy.ts が Cookie を確認 — 速い一次ガード
サーバー が Server Component を実行 — DBから取得しHTMLを組み立て
HTML＋RSCペイロード＋必要なJSを送信 — すぐ見える状態で届く
ブラウザ が表示し、操作部分を有効化 — これを「ハイドレーション」と呼ぶ
ブラウザ Edge（proxy.ts） サーバー（Node.js）
STEP 6 / ルーティング

フォルダ構成が、そのまま URL になる

app/ ├── (authed)/ ← URLに出ない“グループ” │ ├── layout.tsx ← 共通の器 │ ├── page.tsx → / │ └── tasks/ │ └── page.tsx → /tasks └── login/ └── page.tsx → /login
🧩 layout は「器」、page は「中身」
外側の layout（サイドバー等）が、内側の page を包む。入れ子にできる。
📁 (authed) はルートグループ
カッコ付きは URL に出ない。「ログインが必要なページだけ同じ器でまとめる」のに使う。
STEP 7 / データ

表示は「読む」、変更は「Server Action」

📖 読む（表示）
Server Component→DB
サーバー上で DB を直接読んで、そのまま画面に描く。
✏️ 変更（作成・更新・削除）
フォーム→ Server Action→ DB
"use server" を付けた関数を <form> から直接呼ぶ。API を手書きしない。

このアプリでは、失敗は例外を投げず Result 型（成功/失敗）で返すルールにしています。

STEP 8 / 速さと鮮度

なぜ変更が「すぐ反映」されるの？

毎回DBに聞くと遅い。そこで結果をためて（キャッシュ）速く返し、変更したらそのタグを捨てて次回だけ取り直します。

🗄️ ためる
"use cache" ＋ cacheTag("tasks") で結果に名札を付けて保存。
→高速に返す
✏️ 変更が起きる
タスクを作成・削除（Server Action）。
→名札を無効化
🔄 捨てて取り直す
updateTag("tasks") で破棄 → 次の表示で最新を再取得。
STEP 9 / 認証

ログイン確認は「二段ガード」

速い門番と、確実な門番の2人で守ります。

Edge proxy.ts：Cookie があるか？ — 超高速。なければ即 /login
Node.js AuthGate：DBのセッションは有効か？ — 確実。失効していれば /login
両方OK → ページを表示 ✅

Edge では DB を使えないので Cookie の有無だけ確認。本当の検証は DB が使える Node.js 側に任せる、という分担です。

STEP 10 / 動かす

開発するとき・本番で動かすとき

🛠️ dev
開発用。Turbopack で高速ビルド＋保存すると即反映（ホットリロード）。
📦 build
本番用に最適化・圧縮して成果物を作る。
🚀 start
build の成果物で本番サーバーを起動。

Turbopack＝Next.js 標準の高速バンドラ（たくさんのファイルを1つにまとめる道具）。

まとめ / 俯瞰

全体像：1枚で見る

ブラウザ：表示・操作（Client Component / フォーム）
proxy.ts（Edge）：Cookie で一次ガード
サーバー（RSC / Server Actions）：AuthGate で検証 → 取得・変更 → キャッシュ制御
Drizzle + SQLite：データの保管庫

題材アプリ（タスク管理）では：一覧/統計＝Serverで読む、作成/削除＝Server Action、フィルタ＝URL状態、ログイン＝二段ガード。
